Proposta técnica · Segurança & Infra & CTO

Debug em produção sem dar shell no pod

Proposta: substituir o acesso de desenvolvedores a pods via kubectl exec por um endpoint de diagnóstico embutido na própria aplicação — autenticado com Google SSO, restrito por allowlist, com permissão por ferramenta e auditoria de cada comando executado.

autor: jones vitolo agosto/2026 status: para discussão base: cortex_ex v0.6 (implementado)

1 · O problema

Hoje, debugar em produção significa acesso total

Quando um dev precisa investigar um problema em produção, o caminho é kubectl exec no pod e um remote console do Elixir. Isso cria três problemas que crescem com o tamanho do time:

Tudo ou nada

Quem entra no pod tem shell completo e console com poder de executar qualquer código — não existe “só leitura”. Um typo no console pode derrubar o node.

Auditoria cega

O audit log do Kubernetes registra que houve um exec — não o que foi digitado dentro da sessão. Reconstruir o que alguém fez é impossível.

Credencial pesada

Cada dev com acesso significa kubeconfig, RBAC e VPN de cluster para manter, rotacionar e revogar — uma superfície que só aumenta.

2 · A proposta

Diagnóstico como serviço da própria aplicação

O cortex_ex é uma biblioteca Elixir (desenvolvida internamente, ~40 ferramentas) que embute na aplicação um endpoint de diagnóstico via protocolo MCP. O dev conversa com a aplicação — pela ferramenta de IA que já usa ou por cliente HTTP — e cada chamada passa por uma cadeia de verificações antes de executar. Se qualquer etapa falha, a resposta é negada: o sistema é fail closed por construção.

req Dev → HTTPS via Claude ou cliente MCP
gate 1 Token JWT RS256 emitido via login Google (OAuth 2.1)
gate 2 Domínio corporativo só e-mails @empresa.com
gate 3 Allowlist e-mail cadastrado individualmente
gate 4 Nível da ferramenta leitura × escrita por usuário
exec Executa + audita quem, o quê, argumentos, resultado
qualquer gate falhou → 401/negado + registro no audit

3 · O que o dev passa a fazer

35 ferramentas de leitura cobrem o grosso do debugging

A maior parte do que hoje justifica um exec no pod é diagnóstico: ver erros, logs, processos, queries lentas. Tudo isso vira leitura segura — sem shell, sem risco de alterar estado. Escrita é exceção, concedida por usuário.

leitura 35 ferramentas · acesso padrão
get_errors get_logs slow_queries slow_requests supervision_tree process_info oban_queues failed_jobs live_views telemetry_metrics routes +24

Introspecção do runtime: nada aqui altera estado da aplicação.

escrita 6 ferramentas · concessão individual
project_eval retry_job run_impacted_tests run_stale_tests clear_errors clear_logs

Equivalente ao poder do remote console — mas individual, revogável na hora e com cada execução registrada com o código completo.

4 · Modelo de segurança

Seis camadas independentes, todas fail closed

L1
Rede — path exposto em ingress dedicado, atrás de VPN / IP allowlist (decisão da infra)
L2
Autenticação — JWT RS256 validado contra JWKS do identity provider; algoritmos fracos rejeitados; JWKS fora do ar = acesso negado
L3
Domínio — restrição no IdP (conexão Google única do workspace) + verificação do domínio do e-mail na aplicação
L4
Allowlist — e-mail precisa estar cadastrado; remoção vale na requisição seguinte; erro de banco = acesso negado
L5
Permissão por ferramenta — leitura × escrita verificada duas vezes (na listagem e na execução); ferramenta sem classificação é tratada como escrita
L6
Auditoria — toda chamada registrada em banco: ator, ferramenta, argumentos, resultado — incluindo tentativas negadas
# cortex_ex_audit_log — exemplo real do formato
2026-08-11 14:32:07  ana@empresa.com     slow_queries    {"threshold_ms": 500}      ok
2026-08-11 14:33:41  bruno@empresa.com   project_eval    {"code": "MyApp.Repo..."}  denied
2026-08-11 14:35:02  ana@empresa.com     get_errors      {"limit": 20}              ok
2026-08-11 14:38:19  carla@empresa.com   retry_job       {"id": 84213}              ok

5 · Comparativo

Acesso via pod × acesso via aplicação

Dimensão kubectl exec + remote console cortex_ex
Identidade kubeconfig — compartilhável, rotação manual Google SSO individual — a conta que o dev já usa
Granularidade shell completo, sem meio-termo por ferramenta — leitura × escrita por pessoa
Auditoria registra que houve exec; conteúdo da sessão é invisível cada comando com argumentos, inclusive os negados
Revogação rotacionar credenciais, mexer em RBAC remover o e-mail — efetivo na requisição seguinte
Onboarding de dev kubeconfig + RBAC + VPN de cluster URL + login Google
Alcance pod, node, rede, filesystem — necessário para infra/SRE somente a aplicação (proposital)

A última linha é o ponto central da proposta: não é substituir o kubectl — é reduzir drasticamente quem precisa dele. Infra e on-call mantêm acesso ao cluster; devs deixam de precisar.

6 · Limites conhecidos

O que essa proposta não resolve

Se a aplicação caiu, a ferramenta caiu junto

Pod em CrashLoop, OOM, app que não sobe: invisíveis para o cortex_ex, porque o endpoint é a própria aplicação. Incidentes de infra continuam sendo território do kubectl — por isso SRE/on-call mantém o acesso atual.

Múltiplas réplicas respondem individualmente

Buffers de erros e logs são locais de cada pod; atrás do load balancer, chamadas podem cair em réplicas diferentes. A agregação entre nodes é o próximo item do roadmap (v0.7); até lá, o uso indicado é diagnóstico pontual, não visão consolidada.

Permissão de escrita é poder de root na aplicação

O project_eval executa código arbitrário — auditado, mas não impedido. A proposta trata escrita como break-glass: pouquíssimas pessoas, e evolução planejada para concessão temporária com expiração automática.

Rate limiting ainda não existe

Está fora do v0.6. Mitigação no piloto: exposição apenas via VPN + volume monitorado pelo próprio audit log.

7 · Piloto proposto

30 dias, uma aplicação, somente leitura

Escopo mínimo para validar o modelo com risco próximo de zero: uma aplicação, todos os participantes em modo leitura (nenhuma permissão de escrita concedida), endpoint acessível apenas via VPN. Ao final, revisão conjunta do audit log com o time de segurança: o que foi usado, por quem, e se algo pediu ajuste.

Segurança
  • Revisar o modelo de seis camadas e o formato do audit
  • Aprovar o piloto read-only
  • Definir critérios de saída do piloto
Infra
  • Path dedicado no ingress, restrito à VPN
  • Tenant no identity provider (WorkOS/Auth0) com conexão Google do workspace
  • Rodar a migration das duas tabelas (users + audit)
CTO
  • Sponsor do piloto e escolha da aplicação
  • Decidir, ao final, a política de acesso a pods para devs

Resumo em uma frase

90% dos motivos pelos quais um dev pede exec no pod passam a ser atendidos por um canal autenticado com a conta Google corporativa, restrito por pessoa e por ferramenta, e com cada comando registrado — enquanto o acesso ao cluster fica restrito a quem opera o cluster.

O código está implementado e testado (v0.6, 163 testes). O custo do piloto é configuração, não desenvolvimento.
